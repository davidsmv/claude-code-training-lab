Overview

CLAUDE.md, rules, skills and subagents are instructions the model chooses to follow. Only a hook is code that runs no matter what the model decides. MCP adds new abilities, and plugins bundle the rest so you can share it.

The pieces at a glance

PieceWhat it isLoads / runs whenEnforced by
General project instructionsAlwaysThe model
Instructions for certain filesMatching files are touchedThe model
Your code at lifecycle eventsThe event firesYour script, every time
Allow, ask and deny rules, plus modesEvery tool callClaude Code itself
A worker with its own prompt and toolsClaude delegates a taskThe model, isolated
A reusable procedureTask matches, or /nameThe model, main chat
A bundle of skills, agents and hooksInstalled or loadedWhatever is inside
A program that gives Claude new abilitiesWhile connectedThe server's code
API feature to reuse a stable prefixPer requestThe API

Which one do I need?

  • Must always hold, or is a safety limit → hook
  • Applies everywhere → CLAUDE.md
  • A convention for some files → rule
  • A procedure you repeat, loaded only when needed → skill
  • A self-contained task that would clutter the chat, or needs restricted tools → subagent
  • Claude must reach something new (database, Jira, an API) → MCP server
  • You want to share or reuse your setup → plugin

CLAUDE.md

Always-on project memory, loaded into every session.

Confirmed live

Key points

  • Use it for broad guidance: build and test commands, architecture that spans files, constraints that apply everywhere.
  • Keep it short. It costs context in every session, so long procedures belong in a skill.
  • No secrets. It is usually committed.
  • Generate a first version with /init; check what is loaded with /memory.

In this project

This file records the repository layout and validation commands. It deliberately avoids personal machine settings and credentials.

Configure Claude Code

Rules

Narrower instructions in .claude/rules/, loaded only when Claude works with matching files.

Confirmed live

Key points

  • Scope comes from the paths glob in the frontmatter, not from where the file sits.
  • A rule with no paths loads at launch, like CLAUDE.md, even inside a subdirectory.
  • Subdirectories such as .claude/rules/database/ are only for organizing.
  • "Never modify the schema" applies everywhere, so it goes in CLAUDE.md. "SQL here needs explicit transactions" is narrow, so it is a rule.

In this project

---
paths:
  - "src/**/*.py"
---
# Python rules
- Add type hints to all function signatures.
- Every docstring must start with the tag [py-rule]
- Use pathlib.Path instead of os.path
  • .claude/rules/python.md is scoped to src/**/*.py.
  • .claude/rules/database.md is scoped to src/db/**/*.sql, which has no files yet.
  • .claude/rules/database/naming.md has no paths, so it always loads.

The [py-rule] tag proves the rule loaded, since Claude would never write it unprompted. It appeared in src/calculator.py.

Configure Claude Code

Hooks

Your own scripts at fixed points in the lifecycle. A hook fires every time; a CLAUDE.md instruction is followed "most of the time".

Confirmed live

Events

EventWhenTypical use
PreToolUseBefore a tool runsBlock it: exit 2, reason on stderr
PostToolUseAfter a tool ranFormat, test, log. Cannot block
UserPromptSubmitYou send a promptValidate it or add context
StopThe model finishes a turnNotify, clean up
NotificationNeeds permission, or idle 60sSend to Slack or a log
SessionStart / SessionEndSession starts / endsCheck setup / final audit

Key points

  • Each hook has an event, an optional matcher such as Edit|Write, and a command.
  • The command receives the tool call as JSON on stdin.
  • Exit 0 allows. Exit 2 blocks, and stderr is shown to Claude as the reason.
  • Only exit 2 blocks. Any other non-zero code, including the usual Unix failure code 1, is a non-blocking error: the action still goes ahead. To enforce a policy, use exit 2.
  • It applies in every session and permission mode: a guardrail, not a convention.

In this project

// .claude/settings.json (wrapped for reading; PostToolUse is the same with log_edit.py)
"PreToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command",
  "command": "python -c \"import os,runpy; runpy.run_path(os.path.join(
      os.environ.get('CLAUDE_PROJECT_DIR') or '.', '.claude/hooks/block_prod_config.py'),
      run_name='__main__')\"; exit $LASTEXITCODE" }] }]
  • block_prod_config.py blocks any edit whose path contains config/production.
  • log_edit.py appends each edit to .claude/hooks/audit.log.
  • Registered in settings.json (shareable), not settings.local.json (holds the token).
  • Why the long command? It used to be python "$CLAUDE_PROJECT_DIR/.claude/hooks/block_prod_config.py". Only Claude Code sets that variable. Another agent host that read the same settings left it empty, so Python couldn't find the script, exited with code 2, and the hook blocked every edit. Now Python reads the variable itself and falls back to the current folder. ; exit $LASTEXITCODE keeps exit code 2 when a host runs hooks in PowerShell, which otherwise reports it as 1. In Git Bash the variable is unset, so a bare exit keeps Python's code.
Configure Claude Code

Permissions

What Claude Code may do without asking, what it must ask about, and what it can never do. Claude Code enforces these rules itself, so they don't depend on the model following instructions.

Reference from the Claude Code docs

Allow, ask and deny

RuleWhat happensExample
allowRuns without askingBash(git push *)
askAlways prompts, even if an allow rule also matchesWebFetch(domain:github.com)
denyBlockedRead(./.env)
  • Deny wins over ask, and ask wins over allow. An allow rule can't carve an exception out of a deny rule.
  • A rule is a tool name, optionally with a pattern in brackets. A bare Bash (or Bash(*)) matches every shell command.
  • File rules are relative to the project: Read(.env) follows gitignore rules and matches a .env at any depth, the same as Read(**/.env). Use //path for an absolute path and ~/path for your home folder.

Permission modes

The mode sets how Claude Code treats everything your rules don't decide. Set the starting one with defaultMode.

ModeWhat it does
defaultPrompts the first time each tool is used. Shown as Manual in the interface, and manual is accepted as an alias
acceptEditsAccepts file edits, and common filesystem commands such as mkdir and mv, in the working directory
planExplores with read-only actions and doesn't edit your source files
autoRuns without routine prompts, while a background classifier checks that actions match your request
dontAskAutomatically denies anything that would otherwise prompt
bypassPermissionsSkips permission prompts, including for writes to protected paths such as .git and .claude
bypassPermissions is for isolated environments only. The docs say to use it only in containers or VMs where Claude Code can't damage anything. Administrators can turn it off for everyone with permissions.disableBypassPermissionsMode: "disable", which works best in managed settings because users can't override it.
Deny rules still apply in every mode, including bypassPermissions. A mode doesn't cancel them. The danger of a permissive mode is everything else running without a prompt, while the deny list is the only thing left standing.

What a Read deny rule covers, and what it doesn't

Covered

  • Claude's built-in file tools
  • Grep and Glob (best effort)
  • Files named in @ mentions
  • Bash file commands Claude Code recognizes: cat, head, tail, sed, tee
  • Bash redirections such as > file and < file

Not covered

  • A command that reads files without naming them, such as grep -r pattern . run from the folder that holds the file
  • A script that opens the file itself, such as Python or Node

For a hard, OS-level block, use the sandbox. To apply your own logic to the full command, use a PreToolUse hook.

Bash rules have a similar limit: Bash(curl *) stops curl https://example.com but not /usr/bin/curl ... or sh -c 'curl ...'. A rule covers the form Claude usually writes, and it isn't a security boundary.

Hooks can't override rules. If a deny rule matches, the call stays blocked even when a PreToolUse hook returns "allow".

Where permissions live: shared vs personal

FileWho it affectsIn git?
.claude/settings.jsonEveryone who uses the repoYes
.claude/settings.local.jsonOnly you, in this projectNo
~/.claude/settings.jsonOnly you, in every projectNo
Managed settingsEveryone in the organization, and they can't override itSet by IT

The rule for shared files: put in .claude/settings.json only what the whole team should live with. A permissive mode, a broad allow, a secret, or a path from your own machine all belong in settings.local.json.

In this project

The shared .claude/settings.json holds the project hooks. Personal approvals for temporary files belong in the gitignored settings.local.json, not in a file shared with every contributor. Open /permissions to see every rule and where it came from.

Subagents

A specialized assistant that works in its own isolated context and returns only its result.

Confirmed live

Key points

  • Starts with a clean slate: no conversation history, no files you accumulated.
  • Can have its own restricted tools, for example read-only.
  • Only the final report comes back, so your main chat stays small.
  • A rule adds context that Claude applies itself. A subagent is delegation: the work happens elsewhere.

In this project

---
name: python-reviewer
description: Reviews Python files for type hints, [py-rule] docstrings...
tools: Read, Grep, Glob     # read-only
model: inherit
---
You are a Python code reviewer. You start with a clean context...

.claude/agents/python-reviewer.md. The body is its whole system prompt; the description tells Claude when to delegate. Its report starts with Reviewed by python-reviewer (isolated context). Manage it with /agents.

Skills

A reusable procedure that costs almost no context until it is needed.

Built, not confirmed

Key points

  • A folder .claude/skills/<name>/SKILL.md: frontmatter with name and description, then instructions. It can include scripts or templates.
  • Only name and description are loaded at the start. The full text loads when the task matches, or when you type /name.
  • Runs in your main chat and sees everything in it, unlike a subagent.
  • A rule is triggered by which file you touch; a skill by what you are doing.

In this project

---
name: add-function
description: Add a new function to a Python file in src/ following the checklist.
disable-model-invocation: true    # only you can start it
argument-hint: <file> <function description>
---
Request: $ARGUMENTS
1. Read the target file first...
  • disable-model-invocation: true: Claude can't start it; only /add-function does. Use it for anything with side effects.
  • $ARGUMENTS is replaced by what you type after the command.
  • Try /add-function src/calculator.py multiply two numbers. It should end with "Added with /add-function skill".

One SKILL.md, three runtimes

The same skill folder can run in Claude Code, on the Messages API and through the Agent SDK. Each one finds it and runs it differently, so "runs everywhere" is something you design for.

RuntimeHow the skill gets thereWhere it runsWatch out for
Claude CodeFilesystem discovery: .claude/skills/, ~/.claude/skills/, pluginsYour machine, with your shell and toolsIt quietly works with whatever you have installed, so it's easy to depend on that by accident
Messages APIUpload it with the Skills API, then list it in the request's container.skills (type, skill_id, version), up to 20 per request. The request must also include the code execution toolAnthropic's code execution containerNo network access and no package installs at runtime: only pre-installed packages
Agent SDKFilesystem, from the sources in settingSources (TypeScript) or setting_sources (Python). The skills option limits which ones Claude may invokeThe machine running your program, from its cwdSetting settingSources yourself without 'project' drops the project's skills. With an explicit tools list, include "Skill"
Check your course notes on beta headers. Older material says the API needs beta headers such as skills-2025-10-02 and code-execution-2025-08-25. Today's docs say the Skills API is out of beta and the code execution tool needs no anthropic-beta header. The old headers still work, but new code doesn't need them. What doesn't change is that the API runs skills inside a code execution container.

Designing a skill that ports

  • Write a description that says what the skill does and when to use it, without mentioning your own setup.
  • Bundle scripts and reference files in the skill folder and refer to them relative to it, never by an absolute path.
  • If it must run on the API, include no network calls and no pip install step.
  • Don't assume a particular OS, shell, or local tool such as gh, jq or PowerShell.
  • Test it in each runtime you target, not only the terminal you wrote it in.
Subagents start clean, including skills. A subagent doesn't see the skills you already used in the main chat. To give it a skill's full text at startup, list the skill in the subagent's skills frontmatter field. Otherwise it can only discover one and invoke it through the Skill tool. Built-in agents don't preload skills, and a skill with disable-model-invocation: true, such as this project's add-function, can't be preloaded.

Plugins

A folder that bundles skills, subagents and hooks so you can reuse or share them.

Built, not confirmed

Structure

training-plugin/
├── .claude-plugin/plugin.json         <- manifest
├── .claude-plugin/marketplace.json    <- lets others install it from GitHub
├── skills/add-function/SKILL.md
├── agents/python-reviewer.md
├── hooks/hooks.json
└── scripts/block_prod_config.py, log_edit.py

Key points

  • Hook paths use ${CLAUDE_PLUGIN_ROOT}, because the plugin can live anywhere.
  • Skills are namespaced: /training-plugin:add-function.
  • Not included: rules, CLAUDE.md, and never settings.local.json.
  • Test locally with claude --plugin-dir ./training-plugin, then /plugin and /hooks.
  • Validate before you ship: claude plugin validate ./training-plugin checks the manifest and every path, and reports misplaced files. Add --strict to make warnings fail. Only plugin.json goes in .claude-plugin/; skills, agents and hooks sit at the plugin root.
  • Share by pushing the folder to its own GitHub repo (start private). Others run /plugin marketplace add <user>/training-plugin.

Before you share it

  • Paths stay inside the plugin. A path that resolves outside the plugin root, usually one containing .., doesn't load, and claude plugin validate reports it. Use ${CLAUDE_PLUGIN_ROOT} for bundled files and ${CLAUDE_PLUGIN_DATA} for things the plugin installs or caches.
  • Declare the values it needs. Put required settings, such as an endpoint or a token, in userConfig in plugin.json. Claude Code then prompts for them when the plugin is enabled. sensitive: true masks the value and keeps it in secure storage rather than settings.json. MCP config and skill content refer to it as ${user_config.KEY}.
  • Document what you can't prompt for, such as a tool that must be on PATH, and consider a SessionStart hook that checks for it and prints a clear message.
  • Test the install on a clean machine, a fresh user account or a container. Install it from the marketplace, not with --plugin-dir from your working copy. Anything that only works on your machine shows up there.

In this project

Passes claude plugin validate ./training-plugin --strict and both scripts were tested outside Claude. It has not been loaded in a live session yet. With the plugin loaded, the project's own hooks and agent still run too, so you may see two log entries per edit.

Extend & optimize

MCP (Model Context Protocol)

A running program that gives Claude new abilities. A skill tells Claude how; an MCP server gives it the ability.

Confirmed live

Client vs server

MCP has two sides. They talk with a fixed set of messages, so any client can use any server.

MCP CLIENT

Claude Code

The app that wants new abilities. It has an MCP client built in.

  • Starts the server
  • Asks what it offers
  • Sends tool calls, reads resources, fetches prompts
  • Decides how to show them to you
↔ MCP protocol the client asks, the server answers
MCP SERVER

notes_server.py

The program that offers the abilities. It does the real work.

  • Lists its tools, resources and prompts
  • Runs the code behind a tool
  • Sends back the result
  • Knows nothing about the model or your chat
Think of a web browser and a web server. The browser asks for pages and the server serves them. Any browser works with any web server because both follow the same protocol (HTTP). Here, Claude Code is the browser, notes_server.py is the web server, and MCP is the protocol.
MCP clientMCP server
JobAsks for thingsOffers things
In this projectClaude Codemcp-server/notes_server.py
Who writes itAlready built into the app (you can also write your own)You, or you install one someone else wrote
Where it is set up.mcp.json lists which servers to connect toThe Python file itself: @mcp.tool(), @mcp.resource(), @mcp.prompt()
StartsWhen the app startsLaunched by the client (stdio), or already running somewhere (remote, over HTTP)
DecidesWhether to ask your permission, and how resources and prompts are shown (@ mentions, / commands)What exists, and what each tool does

What happens when you ask "search my notes for hook"

  1. When Claude Code starts, its client launches the server and asks what it offers. The tool list ends up in the model's context.
  2. You type the request. The model sees the tool list and decides to call search_notes.
  3. The client sends that call to the server. Claude Code usually asks your permission first.
  4. The server runs the Python function and returns the matching notes.
  5. The client passes the result back to the model, which writes your answer.
The client is not the model. The model decides what to do. The client is the connection that carries the call to the server and brings the result back.

Good to know

  • One server, many clients. We tested notes_server.py with a small script of our own before Claude Code connected to it, and it worked unchanged with both.
  • One client, many servers. Claude Code can connect to several servers at once, for example notes, Jira and a database.
  • The server only offers. It lists resources and prompts, but each client chooses how to show them. That is why support for them varies between clients.

The three things a server exposes

KindTriggered byOur exampleThink of it as
ToolThe modelsearch_notes, add_noteA function Claude can call
ResourceThe client, by addressnotes://list, notes://{note_id}A file attached to the chat
PromptThe user, by namesummarize_noteA saved, vetted instruction

Key points

  • Direct resource: fixed address. Templated: a parameter in the address. Use one when known data should be in context from the start.
  • Prompts matter when exact wording changes the result and every user should get the same quality. They're the least used; many servers have only tools.
  • Tokens: MCP can save them (code written once, work done outside the model), but tool descriptions and big results cost context. Its real value is reliability and reuse.
  • Use the official mcp SDK and pin it: in 2.x FastMCP was renamed MCPServer.
  • Never print() in a stdio server; it corrupts the messages. Use logging.

In this project

  • mcp-server/notes_server.py, registered in .mcp.json with relative paths.
  • Tool: ask "search my notes for hook". Resource: type @ and pick notes:list. Prompt: /mcp__notes__summarize_note 2. Status: /mcp.
  • "Connection closed" at first: the command path was likely wrong (an empty ${CLAUDE_PROJECT_DIR}, not proven). Relative paths fixed it.
Extend & optimize

MCP transport & scope

Two separate choices every time you add a server: how Claude Code talks to it (transport), and who gets it (scope). Most mistakes come from mixing the two up.

Reference from the Claude Code docs
The two questions. Transport answers "where does the server run?" Scope answers "who should have it?" They are independent: an HTTP server can be private to you, and a stdio server can be shared with the whole team.

Part 1: Transport

A transport is the channel between the MCP client (Claude Code) and the MCP server. Pick it by where the server runs.

TransportWhat it isUse it whenAdd it with
stdio Claude Code launches the server as a process on your machine and talks over its standard input and output. The server is local: a script, a database on your laptop, anything that needs your machine's files or tools. claude mcp add <name> -- <command>
HTTP The server is already running somewhere and Claude Code connects to its URL. The server is remote: a cloud service, or something your company hosts. This is the recommended option for remote servers. claude mcp add --transport http <name> <url>
SSE deprecated An older way of connecting to a remote server (Server-Sent Events). Only a legacy server that offers nothing else. Use HTTP wherever you can. claude mcp add --transport sse <name> <url>
STDIO

Claude Code starts it

Like running a script yourself, but Claude Code does it and reads the output.

  • Runs on your machine
  • No network, no URL
  • Dies when Claude Code exits
  • This is what notes_server.py uses
vs who starts the server?
HTTP

It is already running

Like opening a website: Claude Code only needs the address.

  • Runs anywhere: cloud, company server
  • Reached by URL, often with a token in a header
  • Many people can share one running server
  • Keeps running when Claude Code exits
Why not always HTTP? A local tool, such as a SQLite file on your laptop, has no reason to be on the network. Putting it behind a URL adds hosting, authentication and exposure for no benefit. Why not always stdio? A service your whole team uses has to run in one place; each person starting their own copy would defeat the point.

Claude Code also supports a WebSocket transport (ws), for servers that push events on their own. It can only be configured as JSON, and it is rarer, so this lesson focuses on the three above.

Part 2: Scope

Scope decides where the server's configuration is stored, and therefore who gets it. The default is local.

ScopeStored inWho gets itUse it for
Local (default) ~/.claude.json, under this project Only you, only in this project Personal tools, experiments, anything with credentials you don't want in git
Project .mcp.json in the project root Everyone who clones the repo (it is committed) Servers the whole team needs for this repo
User ~/.claude.json, top level Only you, in all your projects Personal tools you want everywhere
Enterprise (managed) Managed settings, set by the organization Every user in the organization Servers IT must deploy, or must block
  • Project scope asks for approval. Claude Code prompts before using a server from .mcp.json, because the file came from the repo. That is why our notes server asked you to approve it.
  • Never put secrets in .mcp.json, since it is committed. Use environment variables instead (${API_KEY}), or local scope.
  • Precedence: if the same server name exists in several scopes, only the highest one is used and they are not merged. Order, highest first: managed, local, project, user.
  • Managed configuration can also be an allowlist or a denylist, so IT can restrict which servers people may connect to.

Part 3: Pick both for a scenario

Ask the two questions in order, then pick one answer for each.

ScenarioTransportScopeBecause
A SQLite query tool used only on your laptopstdioLocalIt runs on your machine, and only you use it
A code search service on company infrastructure, for the whole engineering teamHTTPProject (.mcp.json)It is hosted remotely, and the repo's config shares it with the team
An experimental scraper you are testing this week on one repostdio or HTTPLocalExperimental and not ready to share means local scope. The scenario never says where it runs, so either transport could fit
A security scanner IT must deploy to every developerHTTPEnterprise (managed)It is hosted centrally, and it must reach everyone without relying on each repo
How to read the checkpoint. Each answer bundles a transport with a scope, and each of the four options fits exactly one scenario. Find the scope first: personal or experimental means local, the whole team means project, the whole organization means enterprise. Then look for where the server runs. If the scenario says it runs on your machine, that is stdio. If it says it is hosted, that is HTTP. If it says nothing about where it runs, as in the experimental scraper, no transport is forced, and the "stdio or HTTP" option is the right one. Don't pick a transport the scenario never mentions.

In this project

  • Our notes server is stdio + project: Claude Code starts notes_server.py from .mcp.json, and anyone who clones the repo gets it. A real private server with a token would be local scope instead.
  • To see what is configured: claude mcp list in a terminal, or /mcp inside Claude Code.
Extend & optimize

Prompt caching

Pay once to process a stable prefix, then reuse it at about a tenth of the price.

Confirmed live (by script)

Key points

  • Prefix match: one changed character before the cache point means a miss and a fresh write.
  • Turn it on per request with "cache_control": {"type": "ephemeral"} on the last block to cache. Up to 4 breakpoints.
  • Lifetime is 5 minutes, refreshed on every read. Add "ttl": "1h" for an hour.
  • Short prefixes silently don't cache (minimum about 512 to 4096 tokens, depending on the model).
  • Silent invalidators: timestamps or ids in the prefix, unsorted JSON, changing tools or model.

The request is always processed in this order, so put stable content first:

1. tools2. system3. messages

Review

AI code review

An AI review gives you findings to triage, not a verdict to apply. Trust what it can prove from the code in front of it, test what it can only infer, and keep a person between a finding and anything hard to undo.

Checked against the Claude Code docs

Sort every finding into one of two piles

Provable from the diff

The evidence is on the lines it cites: a missing null or None check, a file or connection never closed on the error path, an off-by-one, a variable used before it is set, a swallowed exception.

Do: open the cited lines and confirm. If the code shows it, fix it.

A claim about runtime or another system

"This will time out under load", "the caller already validates this", "this breaks the billing service", "this query is slow in production".

Do: treat it as a hypothesis. Write a test, run it, check logs or metrics, or ask the team that owns the other system before you act on it.

Why the split works. The Code Review docs say a review "works from reading the diff and the surrounding code, without building or running your code". Anything that depends on running the code, on real data or on another service is outside what the reviewer saw, so it can't have proved it.

Where the human gate goes

Put the check where a finding turns into an action that is hard to reverse, not on every comment.

StepEasy to undo?Gate
Reading findings, posting review commentsYesNone needed
Applying a suggested fix on your branchYes, with gitRead the diff before you commit
Merging, deploying, migrating or deleting data, rotating credentialsNoA person decides, with the evidence in front of them
  • On its own, Code Review doesn't approve or block a pull request, and its check run doesn't conclude as a failure. Read "no findings" as "nothing found", not "safe": the docs warn that a review can miss bugs.
  • If Claude applies fixes for you, keep the irreversible step out of its reach: an ask rule such as Bash(git push *), and no bypass mode.

Raise accuracy: give it your conventions

  • Without them, the reviewer guesses. Is a bare except allowed in scripts/? Must every docstring start with [py-rule]? Is os.path banned? Every guess is a possible false positive or a missed finding.
  • Code Review reads REVIEW.md and CLAUDE.md from your repository. It takes REVIEW.md from the base or default branch, never from the pull request's own changes, so a pull request can't rewrite its own review rules.
  • Your own reviewer (a subagent or skill): put the conventions in its prompt, or in CLAUDE.md and rules files, which custom subagents load too.
  • Ask for evidence: each finding should cite file:line and say whether the code proves it or it needs a runtime check.

Review

Config bug hunt

A cumulative checkpoint: read a few config files, spot what is wrong in each layer, and say in one sentence what it does at runtime. The same handful of mistakes keep coming back, so this lesson turns them into a checklist.

Checked against the Claude Code docs

How to answer

Two parts, every time. Bug: say exactly what is wrong, naming the setting or line. Runtime: one sentence on what happens when it runs, saying who is affected and what fails or leaks. "It's insecure" is not an answer; "everyone who clones the repo can read the production token" is.

The five-question review

Run these five questions over any config file before you trust it. Together they catch almost every planted bug.

1. Is there a secret in it?

Look for: tokens, keys, passwords, Bearer sk-..., an env block with real values.

Fix: reference an environment variable (${NAME}), or move it to a file that isn't committed, such as settings.local.json. If it was ever committed, rotate it, because git history keeps it.

2. Is there a path that only works on one machine?

Look for: /Users/priya/..., C:\Users\..., or an absolute path to your own virtual environment.

Fix: a relative path, or the right variable for the layer: ${CLAUDE_SKILL_DIR} in a skill, ${CLAUDE_PLUGIN_ROOT} in a plugin, ${CLAUDE_PROJECT_DIR} for the project.

3. Is it too permissive for a shared file?

Look for: defaultMode: "bypassPermissions", a bare Bash allow rule, or personal approvals in .claude/settings.json.

Fix: keep shared files narrow, and put personal or permissive settings in settings.local.json. Let IT disable bypass mode in managed settings.

4. Does the guard really guard?

Look for: a hook that blocks with exit 1 instead of exit 2, a Read deny that a script can sidestep, or a Bash(curl *) deny that /usr/bin/curl slips past.

Fix: use exit 2 to block, a sandbox for OS-level enforcement, and a PreToolUse hook when you need your own logic.

5. Right place, right key?

Look for: path: instead of paths:, a skill or hook inside .claude-plugin/, a remote MCP server without type, a plugin path that doesn't start with ./.

Fix: check against the docs, then run the validators below.

The checkpoint, solved

The three files from the cumulative task, one bug in each layer.

File 1: .claude/settings.json configuration layer

{ "permissions": { "defaultMode": "bypassPermissions", "deny": ["Read(.env.production)"] } }
BugdefaultMode: "bypassPermissions" in a shared settings file.
RuntimeEvery session in this repo starts with permission prompts and safety checks off, so Claude runs commands and edits files, even in protected paths such as .git and .claude, without asking, and the single Read(.env.production) deny rule is the only guard left.
FixRemove defaultMode (or use default) and keep the deny rule. Use bypass mode only inside a container or VM, and let IT block it with disableBypassPermissionsMode.
Check your course notes on this one. Today's docs say deny rules still block in bypass mode, so the deny rule isn't ignored. If the course expects "the deny rule is ignored", that doesn't match the docs. The answer that holds either way is the one above: bypass mode removes the safety net, and it is set in a file the whole team shares.

File 2: .claude/skills/migration-validate/SKILL.md packaging layer

---
name: migration-validate
description: Validates migration scripts before they run against production.
---
## Steps
1. Run: /Users/priya/scripts/validate-migration.sh
2. Report validation results.
BugA hardcoded absolute path into one person's home folder.
RuntimeThat script exists only on Priya's machine, so on anyone else's, and on Windows, the command fails with file not found and the production validation never runs.
FixBundle the script in the skill folder and call it with ${CLAUDE_SKILL_DIR}/scripts/validate-migration.sh, which works whatever the current directory is.

File 3: .mcp.json MCP / authentication layer

{
  "mcpServers": {
    "data-warehouse": {
      "type": "http",
      "url": "https://warehouse.example.com/mcp",
      "headers": { "Authorization": "Bearer [example token]" }
    }
  }
}
BugA production bearer token written into a committed file.
RuntimeEveryone with access to the repo, including its git history and every clone, can read the production warehouse credential, and it can't be changed per person or revoked without editing the repo.
FixUse "Authorization": "Bearer ${WAREHOUSE_TOKEN}", set that variable in each developer's environment, and rotate the token that was exposed.
Deploy

Enterprise security

A regulated customer asks the same questions before every rollout: who is acting, where the secrets live, what gets logged, where the data goes, and whether anyone can turn the controls off. None of them is hard to answer up front. All of them are hard to retrofit after a production deployment has failed a security review.

Checked against the Claude Code docs

The questions, and what answers them

They askAnswer withHow
Identity: is the agent acting as a specific user?OAuthFor remote MCP servers that act for the user. Each developer signs in through /mcp or claude mcp login <name>, so tokens are per person and never in the repo. For Claude Code itself: SSO on Teams or Enterprise, with forceLoginMethod and forceLoginOrgUUID in managed settings to require your organization's login
Service credentials: where do machine secrets live?Environment variables"Authorization": "Bearer ${SERVICE_TOKEN}" in .mcp.json, never a literal value. apiKeyHelper or an MCP headersHelper can fetch short-lived tokens from a vault. In a plugin, use userConfig with sensitive: true
Access logging: can you show what the agent did?PostToolUse hookFires after each tool call and appends what ran, and when, to an audit log. Deploy it in managed settings, because only managed settings can disable managed hooks. For metrics and events in your own collector, add OpenTelemetry (CLAUDE_CODE_ENABLE_TELEMETRY=1)
Data residency: where is data processed and stored?Provider and regionClaude API: inference_geo ("us" or "global") per request or as a workspace default, plus workspace geo in the Console for storage. Amazon Bedrock, Google Cloud or Microsoft Foundry: the region of your cloud account, such as AWS_REGION
Configuration control: can a developer turn this off?Managed settingsDeployed by IT and highest in precedence, so users can't override them. Lock keys include permissions.disableBypassPermissionsMode, allowManagedPermissionRulesOnly, allowManagedHooksOnly and allowManagedMcpServersOnly

One managed settings file, three answers

// Windows: C:\Program Files\ClaudeCode\managed-settings.json
// macOS: /Library/Application Support/ClaudeCode/   Linux: /etc/claude-code/
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": ["Read(./.env)", "Read(./secrets/**)"]
  },
  "allowManagedHooksOnly": true,
  "hooks": {
    "PostToolUse": [{ "matcher": "*", "hooks": [{ "type": "command",
      "command": "python \"C:/Program Files/Acme/claude-audit/log_tool_call.py\"" }] }]
  },
  "env": { "CLAUDE_CODE_ENABLE_TELEMETRY": "1" }
}
  • Configuration control: nobody can start bypass mode, and the deny rules apply in every mode.
  • Access logging: the audit hook runs on every tool call, and with allowManagedHooksOnly only managed hooks run. That also stops project hooks such as this repo's block_prod_config.py, so move any you still need into managed settings.
  • An absolute path is fine here, because IT installs the script in the same place on every machine. A personal path in a shared repo file is a different case.
  • PostToolUse only sees calls that succeeded. A call blocked by a deny rule or a PreToolUse hook never reaches it, and a failed call fires PostToolUseFailure instead. If auditors want attempts too, log in PreToolUse as well.
  • Run /status on a developer machine to confirm which managed source is in force.
Why before, not after. Each answer is a setting or a short script. Retrofitting means re-issuing credentials that were already shared, redeploying configuration to every machine, and explaining to auditors why logs you never collected are missing. Settle all five answers in the design review, run the pilot with managed settings already in place, and only then go to production.

In this project

The repo has a small version of the logging answer: log_edit.py is a PostToolUse audit hook. It lives in .claude/settings.json, so any developer can edit or remove it, and an enterprise rollout would move it into managed settings. The only MCP server is a local stdio notes server with no credentials. The hooks also taught a lesson: their commands relied on $CLAUDE_PROJECT_DIR, which only Claude Code sets, and in another agent host the guard blocked every edit. Failing closed is the safe way to fail, but test a guard in every place it will run.

Setup lessons

Problems we hit getting started, and their fixes.

"claude is not recognized"

winget install Anthropic.ClaudeCode put claude.exe in a package folder under %LOCALAPPDATA%\Microsoft\WinGet\Packages\ but didn't add it to PATH. Add that folder to the user PATH, then fully quit VS Code, which caches the environment.

Company gateway

.claude/settings.local.json sets ANTHROPIC_BASE_URL and ANTHROPIC_AUTH_TOKEN. It applies only to this project, is gitignored, and replaces the login menu.

Login menu on first run

Onboarding runs before project settings are read. Load the env values into the shell first:

(Get-Content .claude\settings.local.json -Raw | ConvertFrom-Json).env.PSObject.Properties | ForEach-Object { Set-Item "env:$($_.Name)" $_.Value }

"Could not resolve authentication method"

Plain Python scripts don't read settings.local.json. Run the line above in the same terminal first.
